# 变更流程

改动任何会影响运行状态的东西(升级软件、改配置、动插件)之前,走同一套流程。流程不长,但每一步都有判据。

## 一、改之前先留底

把当前状态复制一份,并记下每个文件的 SHA-256。

- 会话存储和档案是两块不同的东西,要分别留底;会话存储这一块别的备份不覆盖。
- 复制完立刻做一次逐文件比对(大小 + SHA-256)。**比对不过的备份等于没有备份。**
- 记下时间戳,放到回滚目录里,名字里带版本号,例如 `pre-<版本>-<时间>`。

**判据:**比对输出必须是"零缺失、零不一致"。不是"看起来复制完了"。

## 二、一次只改一样

- 一次只动一个目标(一个插件、一次升级、一处配置)。
- 改之前想清楚:**这次预期会变什么**。这句话写下来,下一步要用。

**判据:**改之前能说出"预期变化清单"。说不出,说明还不知道自己在动什么。

## 三、改完立刻对比

- 重新取一次状态,和改之前那份对比。
- 检查两件事:**预期的变化有没有发生**、**有没有非预期的变化**。

**判据:**出现非预期变化,不要继续下一步,先查清楚它从哪来。出现过一次:预期只变一个插件版本,实际多出两项,查下去是同时装的另一个插件。

## 四、验证行为,不只看版本号

版本号对得上,不代表功能正常。

- 挑一件"用户能直接看到"的事去验:界面能不能开、成本数字还能不能读、某个页面有没有内容。
- 验不过就回滚,不要在坏状态下继续叠加改动。

**判据:**能说出一件"我看到了它工作正常"的具体观察。说不出来,就是没验。

## 五、回滚要能立刻执行

- 每个装过的版本,安装包和它的 SHA-256 都留着。
- 回滚命令写在一处(比如更新脚本末尾会打印),不靠记忆。

**判据:**回滚命令能直接复制粘贴执行,不需要现查版本号。

## 六、出问题之后

- 记一份事故记录:现象、直接原因、恢复过程、之后加了什么约束。**不删、不改写成"已经解决"。**
- 事故记录里写清"当时的判断错在哪",因为下次会犯的多半是判断错误,不是操作错误。

## 常见退化

- 备份做了但没验 → 以为有,实际缺;
- 改完只看"安装成功" → 漏掉非预期变化;
- 版本号对就算通过 → 功能坏了没人发现;
- 出事之后只修不记 → 同一个坑再踩一次。
